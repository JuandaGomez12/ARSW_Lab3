# Exercise 3 - RMI Room Reservation System

## Description
A distributed room management system built with Java RMI. Instead of designing a custom message format or using HTTP routes, the client calls methods directly on a remote object as if it were local. The RMI registry acts as a naming service that connects the client to the server-side implementation.

## How to Compile
```
javac Ex3/src/Room.java Ex3/src/RoomService.java Ex3/src/RoomServiceImpl.java Ex3/src/RoomRmiServer.java Ex3/src/RoomRmiClient.java
```

## How to Run
Open two separate terminals.

Terminal 1 - Server:
```
java -cp Ex3/src RoomRmiServer
```

Terminal 2 - Client:
```
java -cp Ex3/src RoomRmiClient
```

## Example
```
=== Room Reservation Client (RMI) ===
Commands: list | get <id> | reserve <id> | release <id> | exit

Enter command: list
  E301 - AVAILABLE
  E302 - AVAILABLE
  E303 - AVAILABLE
  E304 - AVAILABLE

Enter command: reserve E301
Room E301 reserved successfully

Enter command: get E301
E301 - RESERVED

Enter command: reserve E301
ERROR: room is already reserved

Enter command: release E301
Room E301 released successfully
```

## Notes
- The RMI registry is created by the server on port 23000.
- `Room` implements `Serializable` so instances can be transmitted across JVMs.
- `RoomService` extends `Remote` and defines the contract that both client and server share at compile time.
- `reserveRoom` and `releaseRoom` are `synchronized` to prevent race conditions under concurrent clients.

The flow is: the server starts and registers the service object in the RMI registry under the name `"roomService"`. The client calls `registry.lookup("roomService")` and receives a stub, a local proxy generated at runtime. When the client calls `service.reserveRoom("E301")`, the stub serializes the arguments, sends them over TCP to the server, and the server deserializes and executes the method. The result travels back the same way. From the client's perspective, the call looks identical to a local method call.

## Reflection Questions

**1. What is the main difference between calling a remote method via RMI and calling it via HTTP or TCP?**

With TCP and HTTP, the developer manually formats messages as strings, sends them over a socket, and parses the response on the other side. With RMI, the network communication is completely hidden. The client calls `service.reserveRoom("E301")` as if it were a local method call. There is no message format to design or parse. The stub generated by RMI handles serialization, transmission, and deserialization transparently.

**2. What happens if the RMI registry is not running when the client starts?**

The client throws a `ConnectException` or `NotBoundException` immediately when it tries to contact the registry via `LocateRegistry.getRegistry()` and `registry.lookup()`. Unlike HTTP, where a retry or timeout is straightforward to configure, RMI does not provide built-in reconnection logic. The client must handle these exceptions explicitly and decide whether to retry or fail fast.

**3. What are the main limitations of RMI compared to HTTP or gRPC?**

RMI is tightly coupled to Java. Both the client and the server must run on the JVM and share the same interface classes. It cannot interoperate with services written in Python, Go, or any other language. Additionally, RMI does not work well across firewalls or in cloud environments because it uses dynamic ports and requires direct TCP connectivity. HTTP and gRPC, by contrast, work over standard ports and are language-agnostic, making them far more suitable for modern distributed systems.
